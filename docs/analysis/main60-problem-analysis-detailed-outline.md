全章建议控制在 **8–10 页**。所有主结果统一使用冻结的 **60 道题**，不再拆分任何题目来源；C1–C4 只用于解释异质性。虽然共有 900 个候选答案，但统计单位是 60 个 `question_id`，不能把 900 行视为相互独立。

整章的逻辑顺序是：

```text
先确认发生了什么
→ 分离存储、检索及其交互
→ 检验结论能否跨 backbone 成立

```

## 5. 问题分析

本章围绕三条主线展开：

1. **架构线：** 哪种存储与检索组合更有效，二者是否存在交互；
2. **稳健性线：** 架构效果是否跨 Qwen 和 DeepSeek 成立，哪些结果依赖 backbone；
3. **机制与决策线：** 错误发生在哪里，双源融合与 Full Context 何时有效，以及质量收益是否值得相应成本。

### 5.1 总体结果与证据框架

本节只完成两件事：建立全章统一的比较规则，并描述需要解释的总体结果。它不提前宣布因果机制或“唯一最佳系统”。

#### 5.1.1 分析对象、比较地图与统一统计规则

**本小节要说明什么**

- 分析对象包括 Qwen E1–E7、DeepSeek E1–E7 和 DeepSeek Full Context；
- E1–E4 是最接近 `2 种原始存储布局 × 2 种检索系统` 的组件设计；
- E5/E6 是 curated-memory 完整系统对照，不能拆成单一“摘要效应”；
- E7 复用 E2 与 E6 的证据进行融合回答，不是新检索器；
- Full Context 是不经过检索的完整上下文诊断基线，不是 E8 或理论 oracle。

**先建立一张比较地图**

| 比较 | 固定不变 | 改变因素 | 主要回答的问题 | 不能单独证明什么 |
|---|---|---|---|---|
| E3 − E1 | R1、题目、backbone | S1 → S2 | 目录在 R1 下是否有用 | 目录对所有检索器都有效 |
| E4 − E2 | R2、题目、backbone | S1 → S2 | 目录在 R2 下是否有用 | S2 的普遍优势 |
| E2 − E1 | S1、题目、backbone | R1 → R2 完整系统 | 平铺存储上的检索系统差异 | BM25 单一算子的纯效应 |
| E4 − E3 | S2、题目、backbone | R1 → R2 完整系统 | 目录存储上的检索系统差异 | 某个 action 的单独贡献 |
| E5 vs E1/E3；E6 − E5 | 题目、backbone | 内容组织与适配检索 | curated-memory 系统是否值得采用 | 摘要或 R3 的独立因果效应 |
| E7 − E2；E7 − E6 | 已有父系统证据 | 增加第二路证据并融合 | 双源证据能否修复错误 | 新检索算法是否更强 |
| Full Context vs DeepSeek E1 | 问题与原始信息来源 | 选择性检索 → 全量输入 | 信息全部可见能否修复检索错误 | 严格单变量因果效应 |

**全章统一的配对统计包**

凡是同题条件对照，正文或附表至少报告以下内容，而不是只比较两个均值：

1. A、B 两个条件各自的均值；
2. 每题差值 `Δq = Score(B,q) − Score(A,q)` 的平均数和中位数；
3. 基于未四舍五入分数的 win/tie/loss，`|Δ| < 10⁻¹²` 记为 tie；
4. 以问题为重采样单位、10,000 次、固定随机种子的 paired bootstrap 95% CI；
5. F1、Strict、Soft 的方向是否一致，Precision/Recall 用来解释差异；
6. Judge 的 `correct / partial / incorrect` 三分类转移矩阵；
7. Strict 二值化后的 gain、loss、净变化和双侧 exact McNemar 检验；
8. 适用时报告 Evidence Recall、Any-hit、All-hit 及无关证据变化；
9. tokens、model calls、latency 和失败重试成本变化；
10. 一句机制解释，以及一句明确的结论边界。

**统计口径如何执行**

- bootstrap 按 60 个问题聚类重采样；抽中一道题时，必须把该题涉及的所有条件、模型和指标一起抽入；
- F1 和 Strict 是主终点，Soft 是语义敏感性分析；Precision、Recall、Evidence Recall 和过程数据主要用于解释；
- Evidence Recall 只在 58 道 evidence-eligible 题上计算并标明分母；Full Context 的 Evidence Recall 保持 `N/A`；
- 对确认性的 E1–E4 核心 contrast，若报告 p 值，按预设检验族做 Holm 校正；C1–C4、相关性和额外扫描属于探索性分析，可使用 BH-FDR；
- 效果量和置信区间优先于“显著/不显著”；不能用“一个模型显著、另一个不显著”直接声称模型依赖；
- 当前数据只来自一个 conversation，因此区间只表示这 60 道题的题目层不确定性，不能外推为跨 conversation 总体不确定性。

**本小节的产物**

- 一张实验条件与可比性地图；
- 一张统计分析协议表；
- 后续所有图表共用的数据字典与 60 题配对键。

#### 5.1.2 三套系统总体结果与 E1–E7 性能画像

**本小节要说明什么**

- 三套系统在 Precision、Recall、官方 F1、Strict、Partial Rate 和 Soft 上总体呈现什么图景；
- 在 Qwen 和 DeepSeek 内部，E1–E7 各条件分别表现出高 Precision、高 Recall、高 Strict 或高 Soft 的哪种模式；
- “词面最佳”“完整语义最佳”“部分正确最多”是否指向同一条件。

**如何说明和分析**

1. 先给三套系统的描述性总表，但注明 Qwen/DeepSeek 的七条件池化值不是一个可部署系统；
2. 再分别给 Qwen 与 DeepSeek 的 condition × metric 热力图，不先混合两个 backbone 排名；
3. Full Context 单列，不作为 E1–E7 的第八个条件；
4. 对均值相近、区间高度重叠的条件，不根据小数点名次强行判定优劣；
5. 只把异常模式写成后续待验证问题，例如“Recall 较高但 F1 较低是否源于答案过长”。

**本小节的产物**

- 三系统六指标总表；
- 两张 E1–E7 多指标热力图；
- 3–5 条需要在后文验证的现象，不在这里给机制结论。

**结论边界**

- 总体池化均值只用于建立结果地图；
- 不能由总体排名替代同题配对分析；
- Partial Rate 是标签构成，不是越高越好的独立质量分数。

#### 5.1.3 词面评分与语义评分的一致、分歧及解释

**本小节要说明什么**

- LoCoMo token F1 与 LLM Judge 是否对系统得出一致评价；
- 分歧来自同义改写、答案长度、额外信息、遗漏限定条件，还是核心关系错误；
- 为什么报告中必须同时保留两套评分，而不能任选其一。

**如何分析**

- 建立 F1 × Judge 标签交叉表，并按 Judge 标签展示 Precision、Recall、F1 和答案长度分布；
- 报告 F1 与 Strict/Soft 的 Spearman 相关，但把相关性定位为描述性证据；
- 重点筛选四类题：
  1. 低 F1、Judge correct；
  2. 高 F1、Judge incorrect；
  3. 高 Recall、低 Precision；
  4. Strict 相同但 F1 差异很大；
- 对上述候选进行人工复核，区分语义等价改写、冗长噪声、关键词碰撞和实质性事实错误；
- 检查控制答案长度前后，Precision/F1 的系统差异是否仍然存在；该分析用于解释，不声称长度具有因果效应。

**本小节的产物**

- F1–Judge 一致性矩阵和分布图；
- 2–4 个评分冲突案例；
- 一段明确结论：F1 用于可复现论文对齐，Strict/Soft 用于语义完整性，两者互补。

**结论边界**

- Judge 不是绝对真值；
- F1 的可复现性不意味着它能识别所有语义等价答案；
- 不得因某项评分对某条件更有利而选择性报告。

### 5.2 架构线：存储、检索及其交互

本节是报告的核心组件分析。重点不是“哪个 E 编号最高”，而是分别识别存储组织、检索完整系统和二者交互，并用证据覆盖说明答案变化可能来自哪里。

#### 5.2.1 存储组织在不同检索系统下的作用

**核心问题与必要对照**

- `E3 − E1`：固定 R1，S2 主题目录相对 S1 平铺原始 session 的作用；
- `E4 − E2`：固定 R2，S2 相对 S1 的作用；
- 回答目录究竟帮助路径导航、提高证据覆盖，还是只改变文件组织而没有改善答案。

**每个 backbone 必须如何报告**

- 按 5.1.1 的统一配对统计包报告 F1、Strict、Soft；
- 补充 Precision、Recall、Evidence Recall、Any-hit、All-hit 和无关证据变化；
- 给出同题平均差、中位数差、win/tie/loss 和 95% CI；
- 给出 Judge 三分类转移，说明提升来自 `incorrect→partial` 还是 `not-correct→correct`；
- 对比两组存储效应，但把正式交互检验留给 5.2.3。

**证据覆盖与答案变化要联动，而非分别列表**

| Evidence 覆盖变化 | 答案提高 | 答案不变 | 答案下降 |
|---|---:|---:|---:|
| 提高 | 检索改善成功传递 | 可能转为利用瓶颈 | 可能引入噪声/冲突 |
| 不变 | 可能由证据排序或回答变化产生 | 无明显作用 | 可能是利用不稳定 |
| 降低 | 需检查替代证据或 gold 不完备 | 需复核 | 支持检索损伤候选 |

至少报告 `P(Strict correct | All-hit)`、`P(Strict correct | not All-hit)` 及其风险差，并统计“Evidence 改善但答案未改善”的题数。

**本小节的产物**

- 两组存储效应 forest plot；
- Evidence 变化 × 答案变化联动表；
- 一条有边界的结论，例如“目录对 R1 的证据覆盖有帮助，但是否转化为答案提升取决于 backbone”。

#### 5.2.2 检索系统在不同存储表示下的作用

**核心问题与必要对照**

- `E2 − E1`：固定 S1，比 R2 与 R1 完整检索系统；
- `E4 − E3`：固定 S2，比 R2 与 R1 完整检索系统；
- 回答内容排序式检索是否提高多跳覆盖，以及目录导航与内容排名是互补还是替代。

**如何分析**

1. 对 F1、Strict、Soft 使用统一配对统计包；
2. 比较 Any-hit、All-hit、Evidence Recall、多跳证据完整性和无关证据；
3. 统计“检索修复”和“检索伤害”的问题数量；
4. 抽查 query、候选结果、邻近扩展和最终 EvidenceBundle，区分搜索方向错误与证据打包错误；
5. 结合 tokens、model calls 和 latency 判断增强检索是否以更多资源换取质量；
6. R1 rounds 与 R2 actions 是不同操作单位，不能直接用次数大小判断哪一种检索更复杂或更高效。

**本小节的产物**

- 两组检索系统配对效应表；
- 多跳证据覆盖图；
- 检索 repair/harm 数量及代表性 trace。

**结论边界**

- 这里识别的是 R1 与 R2 **完整系统**的差异；
- 不能把全部差异归因于 BM25、某一个 query 或某一个 action。

#### 5.2.3 存储 × 检索交互及题型异质性

**核心问题**

- 目录的作用是否取决于检索方法；
- R2 是否已经替代了部分目录导航作用；
- 架构收益是否集中在某类问题。

**正式交互计算**

对每道题、每个 backbone 分别计算：

```text
DIDq = (E4q − E2q) − (E3q − E1q)
```

- DID > 0：目录对 R2 的帮助更大；
- DID < 0：目录对 R1 的帮助更大；
- DID 接近 0：未观察到明显存储 × 检索交互。

F1、Strict、Soft 和 Evidence Recall 分别计算 DID、平均值与 question-level bootstrap 95% CI；DID 不是简单二值配对，不使用 McNemar。

**题型异质性如何加入**

- 对 C1–C4 分别展示核心 contrast 与 DID 的方向、幅度和逐题分布；
- C1 重点观察多证据覆盖，C2 观察时间细节，C3 观察记忆与外部知识结合，C4 观察直接定位和噪声；
- 类别数为 13/13/7/27，尤其 C3 只有 7 题，因此只作描述性机制解释；
- 不在大量“条件 × 类别”组合中寻找偶然冠军，也不以小类别推翻 60 题主结论。

**本小节的产物**

- 2×2 交互图；
- F1/Strict/Soft/Evidence Recall 的 DID 效果量与区间表；
- “题型—主要困难—更有利架构—证据强度”矩阵。

#### 5.2.4 Curated Memory 系统效果与架构结论

**核心问题与必要对照**

- `E5 − E1`、`E5 − E3`：S3 curated memory 系统相对两种原始存储系统发生了什么；
- `E6 − E5`：在 S3 上使用适配检索系统后是否值得；
- 必要时将 E6 与原始存储中的最佳条件作系统级描述，但不当作纯组件消融。

**如何分析**

- 同时检查答案质量、Evidence Recall、输入长度、调用次数、延迟和一次性建库成本；
- 比较 S3 是否减少噪声、提高直接定位，又是否遗漏时间、限定条件或多跳细节；
- 从原始 session 与 S3 中抽取典型的“正确保留”“过度压缩”“时间失真”“人物混淆”案例；
- 对 `E6 − E5` 检查增加的检索复杂度是否带来稳定的答案收益；
- 结论最终写成“完整 curated-memory 系统”的效果，不归因于摘要或 R3 单一组件。

**本小节的产物**

- Curated Memory 质量—证据—成本综合表；
- 信息保留与遗漏案例；
- 架构线最终证据矩阵：`结论—关键 contrast—效果量—CI—Evidence 联动—适用题型—边界`。

### 5.3 稳健性线：跨 backbone 稳定性与模型依赖

本节不以“Qwen 和 DeepSeek 谁总分高”为中心，而是检验前述架构效果换 backbone 后是否仍然成立。

#### 5.3.1 总体及同条件的 backbone 配对差异

**核心问题**

- 在相同 E 条件和相同题目上，将 Qwen 换为 DeepSeek 后，答案质量、证据过程和资源消耗如何变化；
- 差异由多数题共同形成，还是少数极端题拉动。

**如何分析**

- 对 E1–E7 分别计算同题 `DeepSeek − Qwen`；
- 每个条件报告 F1、Strict、Soft、Precision、Recall、答案长度、tokens、calls 和 latency 的均值差、中位数差、win/tie/loss 与 bootstrap CI；
- Strict 给出完整 Judge 标签转移矩阵；
- 检查模型差异是否随题型变化，但类别分析只作解释；
- 结合答案长度和 Precision/Recall，判断 token F1 差距是否可能受回答风格影响。

**本小节的产物**

- E1–E7 backbone 差异 forest plot；
- Judge 标签转移矩阵；
- 词面表现、语义表现和回答长度的联合解释表。

**结论边界**

- Retrieval Agent 与 Answerer 同时更换，因此这里只能称为**端到端 backbone 差异**；
- 不能把差异单独归因于检索能力或回答推理能力。

#### 5.3.2 关键架构 contrast 的跨模型稳定性

**核心问题**

- 存储组织、检索系统、二者交互、curated memory 和融合效果是否跨模型保持方向和幅度。

**必须比较的 contrast**

- 两模型的 `E3−E1`、`E4−E2`；
- 两模型的 `E2−E1`、`E4−E3`；
- 两模型的 DID；
- 两模型的 `E6−E5`；
- 两模型的 `E7−E2`、`E7−E6`。

**不能只并排看显著性，必须直接计算 contrast-of-contrasts**

```text
CoCq = (Bq − Aq)DeepSeek − (Bq − Aq)Qwen
DDDq = DIDq,DeepSeek − DIDq,Qwen
```

对 CoC/DDD 给出平均差和 question-level bootstrap CI。判读时同时区分：

| 证据状态 | 判定 |
|---|---|
| 两模型同方向，且两边区间均有支持 | 强稳定 |
| 两模型同方向，但一侧区间不确定 | 方向性支持 |
| 同方向，但 CoC 显示幅度明显不同 | 方向稳定、幅度依赖模型 |
| 方向相反或 CoC/DDD 明确 | 模型依赖 |
| 两边均接近零或区间过宽 | 未确定 |

**本小节的产物**

- 跨模型 contrast/CoC/DDD 矩阵；
- 每条核心架构结论的证据等级；
- 一张“哪些可以跨 backbone 概括、哪些必须限定模型”的表。

#### 5.3.3 模型依赖结果的机制解释与证据等级

**本小节要解释什么**

- 当某个架构效果在两模型中不同，差异来自检索覆盖、EvidenceBundle 构造、证据利用，还是回答表达方式。

**固定分析顺序**

1. 先比较 Evidence Recall、Any-hit、All-hit 和 retrieval trace；
2. 若检索证据不同，判断答案变化是否随证据覆盖变化；
3. 若证据相似，检查 Answerer 是否正确使用相同证据；
4. 再比较答案长度、Precision、Recall、F1 和 Judge 标签；
5. 对方向翻转或 CoC 较大的题进行人工复核。

**可使用的判读逻辑**

- Evidence Recall 不同且答案同向变化：支持“检索机制差异”；
- EvidenceBundle 已同样完整但答案不同：支持“证据利用/推理差异”；
- Strict 相近而 F1 差异明显：优先检查答案长度和同义改写；
- F1、Strict、Soft 同时下降：更支持实质性质量差异；
- 以上都不能确认：标为“机制未确定”，不强行解释。

**本小节的产物**

- “模型差异—过程证据—答案证据—代表案例—可信等级”表；
- 2–4 个同题、同条件、不同模型的对照案例。

**结论边界**

- 不据此声称某 backbone 在所有长期记忆任务中普遍更强；
- 当前没有 Qwen Full Context，因此 Full Context 不进入跨 backbone 稳定性检验。

### 5.4 机制线：双源融合与 Full Context

本节使用 E7 和 Full Context 回答两个互补问题：多一路精选证据是否能修复错误，以及完全取消检索、让模型看到全部原文是否更好。

#### 5.4.1 E7 的互补空间、Repair/Harm 与融合机制

**核心问题**

- E2 的原始聊天证据和 E6 的 curated-memory 证据是否真正互补；
- E7 何时修复父系统错误，何时破坏已有正确答案；
- 融合收益是否超过双路检索与融合回答的成本。

**先做两个配对比较**

- `E7 − E2`：加入 curated 证据后的净变化；
- `E7 − E6`：加入 raw-chat 证据后的净变化。

二者均按统一统计包报告 F1、Strict、Soft、Evidence 变化和成本。

**再把 60 题划成互斥且完备的四类**

- **Preserve：** E2/E6 至少一路 Strict correct，E7 仍 correct；
- **Harm：** E2/E6 至少一路 correct，E7 变为 not-correct；
- **Repair：** E2/E6 均 not-correct，E7 变为 correct；
- **Unresolved：** E2/E6 均 not-correct，E7 仍 not-correct。

四类必须合计 60。另用 Judge 三分类与 Soft 分析 `incorrect→partial`、`partial→correct` 等渐进变化，避免 Strict 掩盖部分修复。

**机制如何分析**

- 比较两路 bundle 的来源、gold coverage、文本重合、重复、冲突和边际新增信息；
- 证据并集完整但 E7 仍错：更支持冲突处理或组合推理失败；
- 两路均缺必要事实：仍属于上游信息不足；
- 至少一个父系统正确但 E7 下降：人工检查重复、冲突和无关证据；
- 按 backbone 和题型报告 Repair/Harm，但以 60 题结果为主。

**本小节的产物**

- E2/E6 → E7 状态流向图；
- Repair/Preserve/Harm/Unresolved 数量、比例和区间；
- Evidence 重合/边际覆盖与融合结果表；
- 至少一个融合成功案例和一个融合干扰案例。

#### 5.4.2 Full Context 与选择性检索的四象限诊断

**核心问题与比较锚点**

- Full Context 是否真正解决了选择性检索的信息遗漏；
- 主要锚点是 `Full Context vs DeepSeek E1`；
- `vs E5` 和 `vs E7` 为系统级辅助比较；
- DeepSeek E1–E7 仍须完整报告，不能只挑最有利的选择性检索条件。

**每个锚点建立四象限**

| Full Context | 选择性检索 | 主要解释候选 |
|---|---|---|
| 正确 | 错误 | 检索遗漏、整理或 16k 预算可能是瓶颈 |
| 错误 | 正确 | 精选证据可能帮助注意力集中和去噪 |
| 正确 | 正确 | 检索实现了无明显质量损失的压缩 |
| 错误 | 错误 | 继续检查推理、歧义、时间组合或共同难点 |

**如何分析**

- 报告 Strict 转移矩阵、F1/Soft 同题差、win/tie/loss 和 bootstrap CI；
- 统计 Full Context 的净修复与反向损伤；
- 比较输入 tokens、答案长度、延迟和失败率；
- 按 C1–C4 描述四象限分布，探索 Full Context 主要修复哪类题；
- 对“Full Context 错、精选证据对”和相反案例分别人工复核。

**本小节的产物**

- Full Context 四象限表和标签转移图；
- 净修复图；
- 完整输入与选择性证据的质量—长度对照。

**结论边界**

- `source coverage=100%` 不等于 `Evidence Recall=100%`，后者对 Full Context 为 `N/A`；
- Full Context 不是 oracle，完整信息可见仍可能发生长上下文利用失败；
- Full Context 与 E1–E7 的精确 served identifier 并非完全相同，因此应写成同模型家族下的强描述性诊断，不写成严格单变量因果消融。

#### 5.4.3 融合、Full Context 与选择性检索各自适用的条件

**本小节要整合什么**

- 什么问题适合两路证据融合；
- 什么问题需要完整上下文；
- 什么问题反而由短而精选的 EvidenceBundle 表现更好。

**如何分析**

将以下问题特征与 E7 Repair/Harm、Full Context 四象限联合：

- C1–C4 题型；
- 必要 gold evidence 数量；
- evidence 是否跨 session、跨多轮；
- evidence 在完整上下文中的相对位置；
- EvidenceBundle 的 Any-hit、All-hit 与噪声；
- 输入长度、答案长度、Precision、Recall、Strict 与 Soft。

**需要验证而不是预设为真的机制假设**

- 多跳、跨 session 题是否更容易被 E7 或 Full Context 修复；
- 时间与限定细节是否更容易被 curated memory 压缩丢失；
- 相关内容位于长上下文中部时，Full Context 是否更容易利用失败；
- 精选证据是否通过减少噪声提高 Strict 或 Precision；
- E7 的第二路证据在互补较低时是否主要增加冗余。

**本小节的产物**

- “问题特征—更适合 E7 / Full Context / 选择性检索—支持证据—证据等级”矩阵；
- 题型、证据数量和位置的净修复图；
- 三种信息供给方式的条件化边界，而不是一个无条件冠军。

### 5.5 错误归因线：从错误链定位主要瓶颈

本节把前面的分数差异落到端到端过程上。自动规则只产生“错误候选”，必须经过人工复核后才可以写成机制结论。

#### 5.5.1 端到端错误链与可执行归因标准

**统一诊断链**

```text
原始 source 是否含答案
→ 当前 store 是否忠实保留
→ 检索是否覆盖必要证据
→ 16k EvidenceBundle 是否保留证据
→ Answerer 是否正确利用
→ 融合或长上下文是否产生干扰
→ F1 与 Judge 是否因表达产生分歧
```

**八类候选错误与判定证据**

| 候选错误 | 可执行判定 | 需要查看的证据 |
|---|---|---|
| 存储保真错误 | 原始 session 有事实，S3 缺失或改写失真 | source、S3、locator、时间/人物关系 |
| 纯检索遗漏 | 事实存在于当前 store，但最终 bundle 未命中 | query、trace、候选、bundle |
| 多证据覆盖不足 | 只找到多跳所需证据的一部分 | gold evidence、Any-hit、All-hit |
| 预算截断 | 检索过程曾找到，但 16k bundle 未保留 | trace 与最终 bundle 的差集 |
| 利用/推理错误 | 完整必要证据已在输入，答案仍错 | bundle、answer、推理所需关系 |
| 融合干扰 | 至少一个父系统正确，E7 变差 | 两路 bundle、冲突、E7 answer |
| 长上下文利用错误 | Full Context 含源信息却错，精选证据系统对 | 位置、距离、FC answer、检索 answer |
| 评分表达分歧 | Judge 与 F1 因措辞、长度显著不一致 | reference、answer、P/R/F1、Judge |

**主标签规则**

- 采用“上游优先”：`存储 → 检索 → 多证据覆盖 → 预算 → 利用/推理`；
- 每条记录只给一个 primary cause，但可加 fusion、long-context、evaluation mismatch 等 secondary flags；
- 无法确认时标为 `undetermined`，不得强行归类；
- non-evidence-eligible 题不强做 Evidence Recall 归因；
- All-hit 但答错是利用错误候选，不是自动定论；未命中但答对可能使用替代证据或说明 gold evidence 不完备。

**本小节的产物**

- 错误归因 codebook；
- 一张从 source 到 evaluation 的判定流程图；
- 每类错误适用分母及不可判定范围。

#### 5.5.2 自动候选归因、人工复核与瓶颈量化

**第一步：自动生成候选，而非自动宣布原因**

- 基于 store presence、Evidence Recall、All-hit、trace、bundle、答案标签、E7 状态和 Full Context 四象限生成候选标签；
- 输出条件、backbone、题型下的候选错误分布；
- 自动标签用于抽样和初筛，不能直接当作人工确认的错误真相。

**第二步：设计可复核、尽量低偏差的案例样本**

- 建议复核 16–24 例，每个主要错误类别 2–4 例；
- 同时纳入成功反例和自动规则可能误判的案例；
- 覆盖两个 backbone、主要题型、E7 与 Full Context；
- 若要报告错误类型百分比，必须复核全部相关错误，或使用预先声明的分层随机样本；目的性案例只能解释机制，不能估计总体比例。

**第三步：按统一表格逐例复核**

```text
question
→ raw source / current store
→ retrieval query and trace
→ EvidenceBundle / full context
→ candidate answer
→ Precision / Recall / F1
→ Judge label and reason
→ primary cause / secondary flags / confidence
```

复核表至少记录：

- source 是否包含必要信息；
- store 是否忠实保留；
- 是否命中全部必要 evidence；
- 是否因预算丢失；
- Answerer 是否正确使用已有 evidence；
- 是否存在双源冲突或长上下文定位困难；
- 自动标签是否被确认；
- 最终 primary/secondary cause 与高/中/低信心。

**降低人工复核偏差**

- 第一遍打乱案例顺序，隐藏模型名、条件名和得分，只看内容链；
- 第二遍再揭示系统、trace 与成本，完成最终归因；
- 若可能，让第二位评审复核 20%–30%，报告原始一致率或 Cohen’s κ；
- 若只有一位评审，间隔一段时间重审约 20%，保留标签修改日志；
- 模糊案例保留 `undetermined`，不为了让图表整齐而强制归类。

**如何量化瓶颈**

- 按适用分母报告每类错误的数量和比例；
- 报告 `P(Strict correct | All-hit=true)` 与 `P(Strict correct | All-hit=false)` 及风险差；
- 比较“Evidence 改善且答案改善”“Evidence 改善但答案未改善”“无 All-hit 但答案正确”的题数；
- 对人工复核样本报告自动标签确认率和修正后的类别分布；
- 最后只给“主要瓶颈、次要瓶颈、当前无法确定”三级判断，不宣布唯一错误来源。

**本小节的产物**

- 错误漏斗与错误类型堆叠图；
- 16–24 例可审计复核表，正文展示其中 4–6 例；
- 自动归因确认率；
- Evidence 覆盖到答案正确的转化效率。

### 5.6 决策线：质量、成本与实际采用

本节不再增加新的质量结论，而是把前述效果量、稳健性、错误机制和完整成本转化为系统选型建议。

#### 5.6.1 公平的成本口径与完整在线成本还原

**本小节要回答什么**

- 各方案实际付出了多少资源；
- 实验复用、失败重试和一次性建库是否造成不公平记账。

**成本必须拆开报告**

1. **一次性建库成本：** S2 目录组织、S3 curated-memory 构建；
2. **每题成功路径成本：** retrieval tokens、Answerer 输入/输出 tokens、model calls、latency；
3. **运行维护成本：** 失败请求、自动重试、恢复和人工介入；
4. **评测成本：** Judge 单列，不进入部署查询成本。

**公平核算规则**

- E7 实际在线成本必须包含 E2 检索、E6 检索和一次融合回答，即使实验运行中复用了已有 bundle；
- Full Context 虽无检索调用，但完整上下文输入必须计入；
- R1 rounds 与 R2/R3 actions 只分别报告，不转换成同一种“步骤数”；
- 成功路径与失败/恢复成本分表；
- latency 至少报告均值、中位数、IQR 和 P90，注明网络与服务波动限制。

**本小节的产物**

- 建库、查询、维护、评测四类成本表；
- 每题成本、每个 Strict-correct 答案成本及失败重试成本；
- E7 与 Full Context 的真实在线管线示意。

#### 5.6.2 Pareto 前沿、边际收益与规模效应

**核心问题**

- 哪些条件在质量和成本之间不被其他条件严格支配；
- 增加的 tokens、调用和复杂度换来了多少可靠质量提升；
- 一次性构建成本在不同查询规模下是否值得。

**如何分析**

- 分别绘制 tokens–F1、tokens–Strict、tokens–Soft 和 latency–Strict；
- 按 backbone 分面，Full Context 只进入 DeepSeek 家族的描述性图；
- 标记 Pareto 前沿：质量更低且成本更高的条件视为被严格支配；
- 报告每增加 1,000 tokens、一次调用或一秒延迟对应的质量变化，但不把不稳定比率过度解释；
- 使用 `TotalCost(Q) = BuildCost + Q × QueryCost` 分析 S2/S3 在不同查询量下的摊销与 break-even；
- 对 session 继续增长的情景只作规模推演，不把未实际测试的更长上下文写成实验事实。

**判断原则**

- 如果质量差异很小、CI 高度重叠，应优先考虑更便宜、更简单、更稳定的方案；
- 如果质量收益只出现在一个指标或一个 backbone，应降低推荐强度；
- latency 的小幅差异可能来自网络，不写成架构必然结果。

**本小节的产物**

- 质量—成本 Pareto 图；
- 边际收益表；
- 不同查询量下的累计成本与 break-even 图。

#### 5.6.3 场景化推荐与证据边界内的最终结论

**本小节要回答什么**

- 综合质量、跨模型稳定性、失败机制和成本后，实际应在什么场景选择哪个条件；
- 为什么不能脱离应用需求指定一个“总冠军”。

**分别给出以下推荐，而不是合并成一个排名**

- 最高完整语义质量方案；
- 最佳 LoCoMo 词面表现方案；
- 最低在线成本方案；
- 跨 backbone 最稳定方案；
- 最佳质量—成本平衡方案；
- 适合作为诊断或失败回退的方案。

**每条推荐必须附带的证据**

1. 主质量指标及同题效果量；
2. 95% CI 与 win/tie/loss；
3. 是否跨 backbone 稳定；
4. 主要错误瓶颈；
5. 查询成本和一次性建库成本；
6. 适用题型、部署场景与限制。

**需要明确判断的几个问题**

- E7 只有在净 Repair 稳定、Harm 可控且收益超过双路成本时，才适合作为默认方案；否则更适合特定难题或回退路径；
- Full Context 应由质量—成本结果决定是默认路径、少数困难题路径，还是仅作诊断基线；
- 长记忆持续增长时，要同时考虑 Full Context 输入扩张、S3 维护成本和选择性检索的 Evidence Recall；
- 需要可审计性的场景，应优先考虑能够追踪 source、trace、bundle 与失败阶段的系统。

**本小节的产物**

- “场景—推荐条件—质量证据—稳定性—成本证据—风险—边界”矩阵；
- 一张简洁的系统选择决策树；
- 架构、稳健性、机制和决策四类最终结论摘要。

**最终结论边界**

- 推荐只适用于当前 main-60、当前 conversation、当前两个 backbone 和已经测试的运行协议；
- 动态路由、置信度回退、自动冲突检测和更多 conversations 属于未来工作，不能写成已验证结论；
- 若现有证据不支持唯一最佳系统，应如实给出条件化选择，而不是制造绝对结论。
